CCM & RPM Enrollment — Inputs, Process, Outputs

What's entered by hand, what's pulled automatically, what fires as a side effect of enrolling — for Chronic Care Management and Remote Patient Monitoring.

Input (human-entered / picked) Validation gate Backend process Auto-billing Output
Shared starting point
Pick an existing patient from the Patients roster (gen_patients)
Auto-pulled, not retyped: name, dob, phone, medications, allergies. This is the single source of truth both programs enroll from — no duplicate manual demographic entry.
↓
Care manager chooses which program(s) to enroll the patient into — CCM and RPM are independent, a patient can be in one or both
CCM Enrollment
Input
CCM-specific fields (typed / picked)
  • Chronic conditions — free-text tag list, at least 1 required
  • Insurance — optional text
  • Care manager — defaults to the logged-in user's name
  • Consent date — required, defaults to today
  • Consent method — required (e.g. verbal / written)
  • Linked call — optional: an already-logged call for this patient (e.g. the consent/intake call) shown as a pick list
↓
Validate
Client-side gate before submit
  • Blocks submit unless ≥1 condition is added
  • Blocks submit unless consent_date and consent_method are both set
↓
POST /api/ccm/patients
Insert enrollment record
  • Writes a new ccm_patients row: name, dob, phone, condition(s), insurance, care manager, consent date/method, link back to the roster patient (gen_patient_id)
↓
Auto-draft care plan (AI)
Runs immediately, inline, same call
  • Pulls in parallel: last 3 RPM vitals, last 5 lab results, open care gaps, recent check-in barriers (all keyed to this patient)
  • One LLM call drafts goals, tasks and care team tailored to that actual clinical picture — not a generic template
  • Saved as an editable ccm_care_plans row, status active — never presented as finalized, a care manager reviews/edits it
If this step fails, enrollment still succeeds — the manual "AI Draft" button remains as a fallback.
↓
Auto-bill G0506
One-time comprehensive care-planning code
  • Fires only if the enrollment is linked to a real roster patient (gen_patient_id present)
  • Billed once ever per patient — never monthly, unlike 99490/99439
  • Failure here also does not block enrollment
↓
Link pre-enrollment call (if picked)
Only runs if a call was selected in the input step
  • Inserts a ccm_checkins row using that call's duration as minutes
  • Checks the monthly time thresholds immediately — if the linked call alone already clears 20 min, 99490 (or 60 min → 99487 if the patient is separately flagged Complex CCM) is auto-drafted right away instead of waiting for a future check-in
↓
Output
API response → UI
  • { id, care_plan_drafted, g0506_billed, call_linked, time_auto_billed }
  • Toast message reflects exactly which of care-plan-draft / G0506 actually succeeded
  • Patient now appears in the CCM roster with status active, ready for monthly check-ins
RPM Enrollment
Input
RPM-specific fields (typed / picked)
  • Condition — optional free text (reason for monitoring)
  • Linked call — optional: an already-logged call for this patient (e.g. the device setup/education call)
No separate consent capture in this form — RPM consent is handled outside enrollment, unlike CCM which gates on it directly (see asymmetry note below).
↓
Validate
Client-side gate before submit
  • Only requires that a patient has been picked from the roster — no condition or consent fields are enforced
↓
POST /api/rpm/patients
Insert enrollment record
  • Writes a new rpm_patients row: name, dob, condition, link back to the roster patient (gen_patient_id)
↓
Auto-bill 99453
One-time initial setup & patient education code
  • Fires only if gen_patient_id is present — mirrors G0506's condition on the CCM side
  • Billed once ever per patient, regardless of whether a call is linked (setup/education is assumed to happen at enrollment either way)
  • Failure here does not block enrollment
↓
Link pre-enrollment call (if picked)
Only runs if a call was selected in the input step
  • Inserts an rpm_readings row with all vitals left null, note "Initial RPM enrollment / patient education call", minutes = call duration
  • Checks the monthly time threshold immediately — if it already clears 20 min, 99457 is auto-drafted right away
↓
Output
API response → UI
  • { id, setup_billed, call_linked, time_auto_billed }
  • Patient now appears in the RPM roster
  • Next time staff open "Log Reading" for this patient, vitals + note auto-populate from their last known reading (or normal-range midpoints if none exist yet) — enrollment itself doesn't capture vitals
What happens after enrollment (not part of enrollment itself)
  • Recurring time-based codes are never billed at enrollment — only the one-time codes (G0506 / 99453) are. 99490 / 99439 / 99487 / 99489 (CCM) and 99457 / 99458 (RPM) are drafted later, the moment a month's logged minutes cross each threshold in check-ins/readings.
  • 99454 (RPM device-supply code) is unrelated to minutes — it's checked on every reading based on whether the patient has readings on file for 16+ of the last 30 days.
  • Complex CCM (99487/99489) additionally requires a care manager to manually flag the patient — CMS ties that tier to medical-decision-making complexity, not time alone, so it's never auto-triggered by enrollment or check-in time.
  • Every patient-scoped route re-checks that the record's owner_email matches the caller's API key before reading or writing — enrollment doesn't grant standing access beyond that.
Asymmetry worth knowing: CCM enrollment hard-blocks on consent (date + method) and on having at least one condition recorded — RPM enrollment blocks on neither. Both programs still require separate, program-specific consent to actually monitor/bill under CMS rules; RPM's just isn't captured as a field inside this particular form the way CCM's is.
